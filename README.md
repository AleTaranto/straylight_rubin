# straylight

Rubin Observatory / LSSTCam stray-light, ghost and scattered-light analysis.

Organised **by science topic**. Code and notebooks are versionable; the ~1.4 GB of
inputs and generated products live under `data/` and `outputs/` and are excluded by
`.gitignore`.

> **Not yet a git repository.** The layout is repo-ready — run the commands in
> [Making this a repo](#making-this-a-repo) when you want to start tracking it.

### Conventions

Notebooks run **from their own topic directory** and reach shared resources with
explicit relative paths:

```python
pd.read_csv("../data/raw/stray_light_20260506.csv")
plt.savefig("../outputs/figures/something.png")
```

Notebooks that use the shared modules open with a bootstrap cell that puts
`common/` on `sys.path`:

```python
# --- project bootstrap ---
import sys, pathlib
_common = str(pathlib.Path.cwd().parent / "common")
if _common not in sys.path:
    sys.path.insert(0, _common)
# -------------------------
```

Scripts do the same but anchored to `__file__`, so they work under MPI/Slurm
regardless of the working directory.

For convenience, the repo root also carries symlinks (`de440s.bsp`,
`stray_light_20260506.csv`, `stray_light_20260313.csv`, `src -> common`) so anything
still run from the root keeps working.

#### `statistic_geometry.ipynb`

Answers "what correlates with the `arc` artifact appearing?" across pointing,
surroundings (Moon, bright stars, planets) and telescope state (dome, mirror
covers, mount jitter, image quality), with the confounders handled explicitly —
label epoch, night clustering, and observing strategy. Set `CFG.ARTIFACT` /
`CFG.ARTIFACT_BIT` to re-run the whole analysis on `banana`, `horseshoe`, etc.

The notebook's source is generated by `zemax_geometry/_build_arc_nb.py`, so the
cell code stays reviewable as plain Python: edit that and re-run
`python _build_arc_nb.py` rather than hand-editing 37 JSON cells. **Always
regenerate before re-running** — the committed `.ipynb` has silently lagged the
generator before, which produced a results table with `1e10` odds ratios from the
pre-fix band model.

ConsDB and EFD pulls are cached under `outputs/arc_stats/cache/`; delete a
parquet there to force a refetch. `CONSDB_TOKEN` is read from the environment
and falls back to parsing `.env`, so the notebook runs under a bare
`jupyter`/`nbconvert` kernel as well as in VS Code.

**§6.3 is a deliberate negative result, not an unfinished section.** It asks
which reference frame the arc is fixed in — camera (a ghost), dome, or sky — since
that names the scattering surface. The rotator is decoupled from the parallactic
angle here (r ≈ −0.08), which is what makes the frames separable from telemetry
at all. The answer is that **no frame is identified**: arcs arrive in contiguous
runs, and all these angles drift smoothly within a night, so a run is concentrated
in every frame simultaneously. Against a contiguous-block null that preserves the
run structure, nothing survives a 4-frame Bonferroni (best is sky, z = 1.77,
p = 0.047, threshold 0.0125). The sky frame's z also *decays* as the
arcs-per-night threshold tightens (≈2.7 → 1.3), i.e. significance drops while each
night's direction becomes better measured — the signature of a null result rather
than of a real effect short on data.

Two consequences worth not relearning: the raw `R_excess` in §6.1 and the
`moon_pa_cam` concentration it highlights are **not** evidence for a camera-fixed
ghost, and the Watson U² `perm_p` column is **saturated** — at n=984 vs ~40,000 it
returns the permutation floor for all twelve angles, including `rotator_angle`,
which is *less* concentrated in arcs. Rank angles by the night-calibrated z in
§6.2, never by that p-value.

This notebook is **telemetry-only by design** — it reads no pixel data and the
frame question is left open rather than answered. Resolving it needs a direction
per *exposure* instead of per night, which is a different measurement. The
notebook's closing appendix states that follow-up as a self-contained brief
(measurement, traps, the 13 nights with usable rotator leverage, I/O budget) ready
to hand to whoever picks it up; it is a specification only, and none of it has been
run.

#### All-13-artifact star-geometry analysis

Three files, run in this order:

```bash
cd zemax_geometry
python build_star_geometry.py      # one-time caches: star pairs, ConsDB, EFD
python _negative_control.py        # sanity gate -- must print PASS
python run_all_artifacts.py --perm 2000
```

Answers a narrower question than `statistic_geometry.ipynb`, for every artifact
rather than one: **is there always a bright star at a specific off-axis distance
from the boresight?** It cross-matches the Yale BSC
(`L3_baffle/rubin_one_year_output/ybsc_v5.fits`, V < 4.5) against all 100,235
on-sky exposures on inspected nights and scans 1,759 annuli × 5 brightness tiers.
Outputs are plain text: `<artifact>_summary.txt` × 13 plus
`ALL_ARTIFACTS_SUMMARY.txt`, which is the one to read first.

**The result: only `horseshoe` gets a mechanism, and `tape` gets a distance.**
Horseshoe recovers the L3-baffle annulus [2.00, 2.05]° at z = 43 — independently
reproducing `L3_baffle/horseshoe_detailer.py`'s [1.995, 2.025]° model from the
labels alone, which is also this pipeline's positive control. Tape shows a broad
excess peaking at ~20.8°, confirming the 19.5–22° hypothesis already hard-coded
into the CSV's own `tape_*` columns. Everything else is NULL, CONFOUNDED or
UNDERPOWERED.

**Why the obvious method fails, and what replaces it.** Comparing the artifact
rate inside a candidate annulus against outside gives badly misleading answers,
because labels arrive in bursts and the survey revisits fields — so whichever
annulus that night's field populates looks enriched. Measured here, the largest
crude "lift" reachable by chance alone is **1.5×–5.8×**, so a 4× enrichment is the
*typical value of the null*. Three corrections follow, none optional:

1. **Count nights, not exposures.** The statistic is the number of distinct nights
   with an in-annulus label, so a 100-exposure burst contributes 1.
2. **Two nulls, quote the weaker.** Shifting labels within a night is not enough —
   it cannot see that the labelled nights are themselves a biased sample of
   pointings. Checked directly, that null alone assigns p ≈ 0.01 to labels
   deliberately decoupled from the sky. `scan_recurrence` also transplants whole
   nights and reports the larger p. `_negative_control.py` is that check; it
   **failed** before the second null was added, and its header records this.
3. **Support floors.** A cell needs ≥ 3 nights and ≥ 30 exposures to enter the
   scan, and verdicts require ≥ 20 labelled in-annulus exposures with no single
   star supplying > 50 % of them. Without these, the scan is won by a cell holding
   nine exposures where the null is ~0 and any coincidence gives an enormous z.

Do **not** stratify by field or `target_name`: the annulus indicator is a
deterministic function of pointing and varies within only ~10 of 51,646 0.1° fields,
so conditioning on field removes all contrast. This was tested, not assumed.

Mantel–Haenszel odds ratios and the night fixed-effects logit are retained but
**demoted to supporting evidence** and labelled as such in every file: they are
exposure-level, so a burst inflates their precision.

The frame question (camera / horizon / sky) stays **unanswerable**, for a reason
worth not relearning: 99 % of in-annulus exposures contain exactly *one* bright
star, and two stars at the same radius differ in position angle by a
rotator-invariant constant, so they rotate together. The star ensemble adds no
frame leverage over §6.3's single Moon direction. Those R values are printed as
descriptive diagnostics only.

`sail` is reported as a **sub-label of `tape`**, not an independent artifact: all
704 of its labels are `tape;sail`, so it is perfectly collinear and excluded from
the ranking. Caches live in `outputs/artifact_stats/cache/`; delete a parquet to
force a refetch.

##### LaTeX report

For the long-form version with figures — one chapter per artifact, 81 pages:

```bash
cd zemax_geometry
python build_report.py                       # writes report/*.tex + report/figs/*.pdf
cd report && latexmk -pdf straylight_artifacts.tex
```

`build_report.py` reads `outputs/artifact_stats/evidence.pkl`, which
`run_all_artifacts.py` serialises **as it prints the `.txt` summaries**. Figures
and prose therefore cannot drift apart, and nothing in the report is recomputed.
Re-run `run_all_artifacts.py` first if the analysis changed.

- `report_figures.py` — eight per-artifact figures plus two cross-artifact ones.
  Follows the repo's plot conventions: fixed categorical slot order, one hue
  light→dark for magnitude, diverging blue↔red only for signed quantities,
  hairline grid, selective direct labels. A panel that could not be computed says
  so in words rather than rendering empty.
- `report/straylight_artifacts.tex` — master document; `report/method.tex` is the
  methodology chapter; `report/art_<name>.tex` one per artifact.

Two conventions worth keeping if you edit the figures. Scan plots are drawn as
**points, not lines**: cells below the support floor carry NaN, and a connecting
line would assert a measurement at radii where none was possible — a gap means
"not testable", never "zero". And the per-star panel exists specifically to expose
single-star dominance, so the dominant contributor is colour-emphasised; that is
the check which separates `horseshoe` from `smudge`/`sail`/`airplane`.

## Reorganisation and rollback

`reorg.sh` performed the move; `undo_reorg.sh` is its line-for-line inverse and
restores the previous flat layout. Neither script deletes a file — `undo_reorg.sh`
uses `rmdir`, which refuses non-empty directories.

The round trip was verified: `reorg.sh` → `undo_reorg.sh` reproduced the original
162-file manifest (size, mtime and path) exactly, with all 56 code checksums
matching. A baseline manifest is kept outside the tree at
`~/.straylight_baseline_<timestamp>/`.

Both scripts support a dry run:

```bash
MV="echo mv" MKDIR="echo mkdir -p" LN="echo ln -s" bash reorg.sh
```

Note that **rollback does not revert the code edits** (import shims, `../data/...`
paths, token scrub) — only the file moves. Once this is a git repo, prefer git.
